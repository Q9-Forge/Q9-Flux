2. **Timebox on problems**: If a step really gets stuck → don't grind on it,
   set it to ⛔ instead, document the problem under "Parked", discuss it
   with Andreas, and keep working on the next independent step in the meantime.
3. After every completed step: update the status here,
   and also update context.txt at the end of the session.
4. **Save immediately (limit protection)**: After every completed step and
   after every change to ARBEITSPLAN.md/context.txt, immediately `git commit` +
   `git push` — don't wait until the end of the session. Session limits can

   be lost. WIP commits are explicitly allowed.
5. **Only 🟢 Ready gets worked on** — 💡 Proposals and 💤 Idle items stay put

### Phase 4 — Processes (approved 2026-07-04, concept discussed with Andreas late on 2026-07-03)

Fundamental decision **E8** (PROJECT.md): **step model instead of stack switching** —
WASM has no notion of stack switching, so the scheduler manages process **states**
(Active/Waiting/Sleeping) and, on each `q9_kernel_step()` tick, calls the next active
process as a step function. Blocking = a state change plus a wake reason, never a
frozen stack. Execution is swappable per language byte (internal/C =
step function on the kernel stack; 68k later = Musashi context; WASM = instance) —
so the emulated processes end up being the simplest ones. F$Fork is OS-9-semantic
(a new process from a module, not a Unix fork) and builds directly on the module directory
from Phase 2 (Fork = F$Link + descriptor + active queue). Scheduler internals
(F$AllPD & co.) stay 🚫 as sorted out in docs/SYSCALL_ROADMAP.md.

### Phase 5 — 68k runtime (Musashi) — **renumbered evening of 2026-07-04, see decision E11**

**Not yet planned in fine detail** — deliberately deferred to its own,
thorough planning round (like Phase 3/4), not done in passing. This phase was
numbered "Phase 6" until the evening of 2026-07-04; the old "Phase 5" (Shell)
is now **Phase 6** (see there) — reason: decision E11.

**Rough outline from today's discussion** (starting point for
detailed planning, not finished steps):
- Integrate Musashi as the 68k CPU core — natively as an ordinary C library
  (no WASM layer needed), compiled to WASM in the browser (runs there efficiently
  via the browser's own WASM engine, not "double-emulated" in
  the performance sense).
- `Q9_MOD_M68K`: load and run real PIC 68k programs (vbcc toolchain
  still to be obtained, see docs/TOOLCHAIN.md "Not yet installed").
- TRAP→syscall bridge (a Musashi trap calls `q9_syscall`), analogous to
  the `wasmproc.c` bridge from 4.7, but at the level of CPU emulation rather than a WASM import.
  **PIC is mandatory for 68k modules** (like real OS-9) — no relocation table
  needed if vbcc consistently generates PC-relative code.
- A real scheduler at the Musashi level: CPU state (registers + stack pointer in
  emulated RAM) is a plain data structure, savable/restorable at
  every instruction — the real counterpart to the step model from E8, just
  one level deeper, with real stop/resume instead of a cooperation requirement.
- That's the prerequisite for Phase 6 (Shell): a shell built before this
  phase would inevitably just be another `Q9_MOD_NATIVE` or
  short-lived WASM workaround (the E9 trap), not a real, long-lived process.

**Target CPU: 68030** (decision E12, 2026-07-04) — the MMU stays unused rather than
disabled. Important constraint for later: our 68k code (vbcc) should
stick to an instruction set that the real CPU32 target hardware also
knows — the emulator is allowed to be "richer" than what we actually use.

### Phase 6 — Multiple target architectures (💡 Proposal, 2026-08-11, discussed with Andreas)

Andreas wants to extend Q9 Forge beyond the Motorola 68K family:
**RISC-V32**, **ARM64** (a native Q9 port already started, the concrete
Mac model still open) and **x86 32-bit**. For x86, the mode question has been
settled: "32-bit real mode" doesn't exist on x86 (real mode is necessarily
16-bit) — the target mode is **protected mode, flat**, modeled on OS-9000 on
386+ (Microware's own portable, C-written OS-9 successor for
386/68020+/PowerPC/MIPS/SPARC; boot-sequence details not verified against a
primary source, but architecturally the only possible basis for a
portable 32-bit kernel).

Two fundamentally different build types per target architecture (details/terms
in `Q9Forge/AI_CONTEXT.md`, section "Multiple target architectures"):

- **Type A — board emulator**: full hardware emulation (CPU + board),
  runs on Linux/Windows/Mac, executes unmodified guest code. Today's
  Q9 Flux build type, so far only for Motorola 68K.
- **Type B — native runtime**: Q9-OS natively compiled for the
  target architecture, runs directly on real hardware/a real host kernel, no hardware
  emulation, only a thin HAL translation of the syscalls. Corresponds to the
  archived mini-kernel concept (`Q9RESUME-Kernel`).

Today's state is deliberately just structure/planning (ROADMAP.md +
AI_CONTEXT.md updated) — no code work yet. All three
target architectures are ranked roughly equal, with no prioritization.
